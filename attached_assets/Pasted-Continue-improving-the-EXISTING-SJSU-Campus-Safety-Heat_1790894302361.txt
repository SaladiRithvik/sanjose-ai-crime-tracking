==================================================
STEP 1 — ANALYST CAN REMOVE EXISTING HEAT MAP POINTS
==================================================

When an ANALYST views the heat map, give them moderation controls for existing approved reports / heat map points.

Normal users should NOT see these controls.

For analyst users:

- clicking an individual report marker should open its details
- include a button such as:

[ Remove Report ]

or

[ Remove From Heat Map ]

When the analyst removes a report:

1. Show a confirmation dialog:
   "Are you sure you want to remove this report from the heat map?"

2. If confirmed:
   - remove or mark the report as removed in the shared database
   - remove it from the heat-map data source
   - recalculate/update the heat map immediately
   - remove the marker from the current map view

3. The removal must persist after:
   - refreshing the page
   - logging out and back in
   - another user opening the application

Do NOT only remove the point visually from the current browser session.

The database must reflect the change.

If useful, use a status such as:

pending
approved
denied
removed

Only reports with an APPROVED status should contribute to the public heat map.

STEP 4 — FIX REPORT DATA PERSISTENCE
==================================================

This is a CRITICAL fix.

Currently reports appear to exist only in the browser/session of the person who created them.

This is incorrect.

ALL submitted reports must be stored in a SHARED Replit database so that:

- User A can submit a report
- User B can open the app from another browser/device
- Analyst can see User A's pending report
- reports remain after page refreshes
- reports remain after restarting the app

Do NOT rely on:
- localStorage
- sessionStorage
- browser-only arrays
- client-side state

for the authoritative report database.

Use the existing Replit database / PostgreSQL / Replit DB solution already available in the project.

If a database already exists, use it rather than creating a second unrelated storage system.

==================================================
STEP 6 — SUBMIT REPORTS TO THE DATABASE
==================================================

When a user submits a new report:

1. Validate/prepare the report
2. Insert it into the shared reports database table
3. Set:

status = "pending"

4. Confirm the database write succeeded
5. Show a success message

Example:

"Report submitted for review."

The report should then become visible to analysts from any browser/device.

Do NOT mark user reports approved automatically.

==================================================
STEP 7 — ANALYST REVIEW MUST USE DATABASE DATA
==================================================

The Analyst Review Dashboard must read pending reports from the shared database.

Do NOT rely on client-side demo arrays as the main source.

The analyst should see all database reports where:

status = "pending"

When approved:

update database:
status = "approved"

When denied:

update database:
status = "denied"

Then automatically load the next pending report.

The change must persist globally.

==================================================
STEP 8 — HEAT MAP MUST USE APPROVED DATABASE REPORTS
==================================================

The public heat map should read APPROVED reports from the same shared database.

Only include reports where:

status = "approved"

Do not show:

pending
denied
removed

reports in the public heat-map layer.

When an analyst approves a report:

database status changes
→ heat-map query includes it
→ heat map updates

When an analyst removes an existing report:

database status changes to "removed"
→ heat-map query excludes it
→ heat map updates

This should work across different users/devices.

==================================================
STEP 9 — REAL-TIME / REFRESH BEHAVIOR
==================================================

If full real-time synchronization is simple with the current stack, use it.

Otherwise, implement reliable refresh behavior.

At minimum:

- heat map refreshes when opened
- analyst queue refreshes after approval/denial
- submitting a report writes immediately to the database
- browser refresh loads the latest database data

Do not make users depend on stale client-side state.

==================================================
STEP 10 — DATABASE FAILURE HANDLING
==================================================

Add simple error handling.

If saving a report fails:

Do NOT pretend it succeeded.

Show:

"Report could not be saved. Please try again."

If loading analyst reports fails:

Show:

"Unable to load reports."

Log useful technical details for debugging.

Do not silently fall back to browser-only storage.
